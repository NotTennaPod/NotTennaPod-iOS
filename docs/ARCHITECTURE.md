# Architecture

NotTennaPod is a UIKit app over a shared Swift package. Domain logic, persistence and playback live in `NotTennaPodCore`, separate from the screens. Setup, build and test commands are in the [README](../README.md).

## Targets

`Package.swift` defines `NotTennaPodCore`, the two native targets it uses (`NativePCMTransport`, `SQLiteBudget`) and its host tests. `project.yml` generates the Xcode project (`xcodegen generate --spec project.yml`) with the app, extensions and test targets.

| Location / scheme | Purpose |
| --- | --- |
| `Sources/NotTennaPodCore`, `Tests/NotTennaPodCoreTests` | Shared behaviour and host tests, run on the Mac without a Simulator. macOS support exists for development and testing only. Local HTTP fixtures bind 127.0.0.1 with synthetic data and credentials. |
| `Sources/SQLiteBudget` | The `ntp-budget` SQLite VFS (C) that bulk synchronization writes go through (`Sync/Archive/SQLiteWriteBudget.swift`): armed with a byte budget, it refuses a write that would grow the database's files past it; unarmed, it only delegates. |
| `App/`, scheme `NotTennaPod` | The iOS 27+ app, with its SQLite library in Application Support. The scheme runs the UI journeys in `AppUITests/`; its test pre-action starts every loopback fixture server (`Tools/test-fixtures.sh`) and its post-action stops them. |
| `AppTests/`, scheme `NotTennaPodViewTests` | App-hosted UIKit checks with isolated libraries and muted playback. They cannot prove real touch input, acoustic output or background delivery. |
| `Widget/`, `WidgetShared/` | Home Screen player widget and Control Center control (WidgetKit). The app writes the player snapshot into the App Group `group.org.nottennapod.app` (`PlayerWidgetRuntime`); "playing" is a lease the app renews about once a minute while it plays, so the widget and the control turn to paused a few minutes after the app ends without notice (`PlayerWidgetLease`, which states the limits). The buttons are `AudioPlaybackIntent`s in `WidgetShared/`, compiled into both targets and run by iOS in the app's process. `PlayerWidgetModel.swift` is Foundation-only because the extension compiles it without the package. |
| `ShareExtension/` | Share-sheet entry that hands links and feeds to the app. |
| `ProbeTests/`, scheme `NotTennaPodProbeTests` | Real TLS and proxy protocol probes against the local fixture servers. |
| `TestSupport/` | Fixture servers, Android-format test libraries, expected results and media the tests read. |

UI tests tap with `tapWhenSettled` and type with `typeTextSettled` (`AppUITests/NavigationQueries.swift`) because iOS 27.1 accessibility frames lag the keyboard animation. The host suite runs with `--no-parallel` because synchronous waveform work interferes with live-clock tests; concurrency inside tests stays enabled. Debug-only test library IDs isolate tests without touching user data.

## Feeds and storage

`FeedParser.parse(_:now:)` produces metadata and ordered episode snapshots; `FeedAddress.prepare` handles subscription addresses. `FeedFetcher.fetch` takes validator, credential and force inputs and returns updated or unchanged results. Its injected `FeedHTTPTransport` allows deterministic tests; share the ephemeral `URLSessionFeedTransport` where requests must share cookies. `AppDelegate` supplies the app-version User-Agent, proxy and saved credentials; `FeedAuthentication` owns Keychain secrets and SQLite identities and their cleanup. Redirects are proposals to the repository, not commits at fetch time.

Initial insertion keeps duplicate entries, starts them unplayed and fills missing dates from the injected clock before ordering; refresh has different merge rules. `LibraryFeed.metadata` excludes episode snapshots. An empty parsed funding list means the source had none, so refresh keeps existing funding; a missing MIME type stays nullable, and `hasStoredChapters` distinguishes stored presence from loaded content. Preserve these data contracts.

`FeedLibraryStore(url:)` requires an existing parent directory. It owns atomic IDs, records, refresh logs and deferred work; `FeedRefreshService` rereads current state at commit so concurrent playback and preference changes survive. A 304 response or cancellation keeps saved data. Default reads use date order; filters and sorts have their own owners. The database is **schema 22**; `LibrarySQLite` migrates an older library one version at a time, and the version that adds each part is given in brackets. Besides the feed, episode and queue tables it holds swipe-Undo identity guards (13), the restore tables (14), per-feed change generations (`feed_changes`, 15–16), a kind column on pending effects (17), an index of download jobs by episode (18), the server-mode `ntp_*` tables (19; Recording, below), empty in a standalone library, the library tables every library reads (20, `Libraries/LibraryIdentity.swift`): `library_identity` (the library's identity, its Cast tag, the Keep at logout that archived or converted it, and `paths_root`, the folder its owned paths were written under), `statistics_units` (imported Android rows that count separately in statistics, owned by local episode IDs) and `pinned_feed_removals`, and the derived list data (21, `EpisodeListKeys.swift`): `episode_list_keys` (every value a list orders, filters or counts by, derived from `episodes.record` with its staged-hidden and feed-eligibility flags; a podcast hidden while its rows change in bounded transactions is left out when read, so hiding or revealing it rewrites none of its rows) and `feed_list_counts` (each feed's visible counts), kept exact by SQLite triggers on every write path, with two more indexes of those keys (22): every name a stored path's last component gives (`episode_list_keys_file_name`, so a file's owners are read by name alone) and the NEW episodes by podcast (`episode_list_keys_new`, for Remove all from Inbox). The triggers update separate column groups only when a value changed, so a playback save maintains only the indexes it changes (the five-second save writes seven pages whatever the show notes or the library: the episode, session and change-generation rows, the key row, and the history, has-history and last-played indexes whose keys every listening save moves); a record that is not valid JSON is keyed with defaults and never blocks a write; no derived table has a constraint other than its `INTEGER PRIMARY KEY`, and the hidden-row tables they read exist in every library. Schema 21 also holds `feed_changes.details_generation`, the `library_change_sequence` seed, `feed_refresh_memo` and the release ledger's pending indexes. The migration creates them empty with their triggers, so every key row is counted once, when it is made, whoever makes it; a library with episodes (or a release ledger) then fills them after its graph starts (`fillDerivedData`, resuming from `derived_fill` after a relaunch) in short transactions sized by the records' bytes (about 25 ms of CPU each, at most 1,000 episodes, whatever the show notes' length). The ledger's three pending indexes are the one exception to that bound: each CREATE INDEX is one atomic statement that reads the ledger once, so each runs alone in its own step, once per library, in time proportional to the ledger. `derivedReady` says when everything is complete; until then a consumer of derived data reads the canonical tables or waits, and a failed step is reported (`derived.failure`) and retried with growing delays. A database import builds them once at its end, in its own transaction. A sync publication's switch is charged one counted row write for each episode it reveals into a shown podcast (its hidden marker, its list keys and its podcast's counts). `LibraryReader` (a quick and a bulk read-only connection, `readers()`) serves screen reads in one read transaction each, with interrupts scoped to one request and visibility probed by each feed's own key; the graph closes them before the store and before any file moves. Owned paths written under another folder are rewritten onto the current one before a writable open.

An unchanged refresh decodes no stored episodes (`FeedRefreshMemo`): a feed's memo (`feed_refresh_memo`) records that merging a parse, with given inputs, into the stored episodes (as `feed_changes.details_generation` names them) changed nothing. A later refresh with the same parse, inputs and stored details writes only what that merge would have written (the header by the merge's own rule, the recovery log entry and a followed redirect). A details change, an insert, a removal or a move of an episode retires the memo, and so does, in a server library, any write to the tables its episodes are matched and observed by; playback and marks do not. A page other than the first, a local folder and an ambiguous pool (stored or incoming episodes sharing an identifying value or a media address, a repeated or unidentifiable item) are always merged.

The screens read the whole library only when one opens (`FeedLibraryStore.screenSnapshot()`, the snapshot with each episode's stored order key, the folder links and the commit sequence, in one read transaction). After that each screen keeps itself current from the library's committed change sets (`LibraryChangeHub`) through `LibraryScreenUpdater`. A change set (`LibraryChangeSet`, its origin this device's own action or synchronization) is the visible difference one write transaction committed: `LibraryChangeCapture` installs TEMP triggers on the write connection only (nothing in the library's schema or file) that record each key's image at its first touch in the transaction and, before COMMIT, compare it with the key's image then, so only real differences are reported and a rollback takes the captures with it. The updater reads, in one read transaction of the quick reader, exactly the feeds, episodes, statistics units, folder links and queue the pending sets named (`LibraryMirrorRequest`), applies the result only when that transaction saw exactly the delivered commits, and patches `LibraryScreenMirror` (the screens' feeds, queue, deletion targets, units and per-feed counts). A write's receipt (`emitted` read after it) lets an action wait until its screen shows it (`settle`). The open list (Inbox, Episodes, Favorites, History, a podcast's page) keeps its full membership in an `EpisodeListIndex` (chunked ordered storage); Queue and Downloads are recomputed from those collections. `App/LibraryViewController+ScreenPatch.swift` applies a patch to the loaded pages: rows that leave, join or change, the first visible row kept in place, counters from the counts. Sync-only patches are paced to one a second; in the background the sets accumulate and are applied once at activation; a catch-up larger than 2,000 episodes (or a quarter of the open list) opens the screen again. The other screens patch too (`App/LibraryViewController+OtherScreens.swift`): Home keeps its sections in `HomeScreenModel` (the Inbox's eligible NEW in an `EpisodeListIndex`, each subscribed podcast's Get surprised pick from its population of unplayed episodes with media, checked against the clock at every patch and picked again from that podcast's recent population only when it leaves, Classics loaded only at Home's open or return and when the subscription set or a podcast's state, title or cover changes) and draws again only a section whose content changed (a save that only moves a playing episode's position or listening times updates its rows and cards in place, and a row being swiped keeps its view until the swipe ends); Subscriptions, Archive and the drawer order and filter the podcasts by the kept counts and newest dates (`FeedLatestDates`), never by scanning episodes, and patch only the tiles that moved or changed (refresh failure included); a library search keeps every match of its query (`LibrarySearchMatches`) and re-matches only changed episodes and podcasts, never scanning again (not even after a catch-up); Statistics and Feed Information statistics load on open, on their return and on a statistics event (filter, reset), never on routine changes, as Android's fragments do; the episode pager and the player read their episode and podcast by key (the player through `playerFeedHeader` for a podcast no list shows); the Download Log reads at most once a second while shown (`PacedRefresh`).

Nothing decoded and library-sized is kept beyond the screens' library. The store reads every feed's episodes from the database each time it needs them (no decoded cache between reads), and the screens' library holds each episode as lists show it (`LibraryEpisode.listProjection`: SQLite leaves out the show notes and chapters, which are never decoded for it). An episode's page reads its show notes and chapters by key through `LibraryDetailReader`, a read-only connection the screens use synchronously, and a library search matches episode text in SQLite (a new query's scan on the bulk reader, a patch's changed episodes through the detail reader). Statistics read projections at their events. The routine readers outside the screens read keys and counts, not records: automatic download selects from the derived keys of the NEW (or pending release), queued and downloaded episodes and decodes only what it cleans; a file's owners are found by the stored file name (`episode_list_keys.local_file_name`, schema 22) and compared exactly; Remove all from Inbox and Clear history read only the rows they change; the release ledger is read through its pending and unnotified partial indexes; gpodder actions are matched by the GUID and media URL indexes. Each keyed path falls back to the canonical read until the derived keys are complete. Every episode write names what it may change (`EpisodeWriteScope`): a user-state write that would change the stored details (a projection written back) is refused. Decoded covers are kept up to 48 MB and dropped when the app goes to the background and on a memory warning.

Artwork has its own network rules (`MobileImageAccess`) and caches (`App/ArtworkImageCache.swift`). On a restricted network (cellular, a hotspot, Low Data Mode) a picture over 5 MiB waits for an unrestricted network instead of downloading (Android downloads it): it is deferred, never remembered as failed, and asked for again once the network is unrestricted. No picture over 50 MiB is held on any network, and with "Cover images" off for mobile updates a restricted network shows only pictures already on the phone. One source copy of each picture is kept on disk (the Caches folder) and every size the app draws is made from it, so a cover is downloaded once for the lists, the player and notifications; like AntennaPod's `ResizingOkHttpStreamFetcher`, a picture of at most 1 MiB is kept as it is and a larger one is reduced to at most 1,500 px. That folder is trimmed to 250 MiB, least recently used first, at launch, when the app goes to the background and after every 32 new covers. A streamed episode's chapter pictures, whose media has no revision proving that a disk copy still belongs to it, keep their sources in memory only (at most 64 MiB). These budgets are separate from the 48 MB of decoded covers.

Android backup interoperability is separate from internal storage: `AndroidDatabaseBackup` writes and `AndroidDatabaseRestore`/`AndroidDatabaseUpgrader` read Android AntennaPod-format databases (currently the format of 3.12.1, the release the app is built around). OPML and HTML export likewise match Android exactly. The automatic backup (`AutomaticDatabaseExport`, `App/AutomaticDatabaseExportRuntime.swift`) writes each backup under a visible incomplete name unique to the attempt (`NotTennaPodBackup-<UUID>.incomplete`, never a backup name), verifies it, and only then gives it its dated name, never replacing a file; an earlier attempt's incomplete file goes with the next run, and retention keeps the five newest verified complete backups (content it cannot check, such as a file kept only in iCloud or one it cannot read, is kept, never counted and never removed) and touches no other name. A run the app starts holds the background grant, a processing window's expiration completes its lease at once, a bounded successor request is submitted before every run, and whatever a cancelled run reports later is ignored by attempt identity. A manual export (`DocumentExportOperation`) is recorded before the Save picker appears (`ExportAttemptJournal`, `Export Attempts/` in the root folder), with the picked document and its access added before any payload work and the payload's size and digest before publication; a step whose record cannot be saved fails the export before it reads or writes. It holds the background grant while it writes and starts only when admitted (without time it parks at once); when the time ends, cancellation reaches the publisher and its file coordination (a coordination still waiting stops and changes nothing; an accessor already running finishes and counts), and it starts again, with a fresh read, when a scene is active, once any earlier publication of the attempt has settled. Its payload is staged and verified, then published in one coordinated step: replaced as a whole where the provider allows it within the document's scope, otherwise written in place. An attempt that was neither cancelled, published and verified, nor shown as failed (the app ended in the picker's handoff or while writing) is recorded at the next graph start as a pending notice: an export may be incomplete and its location is unknown, or the named document may be incomplete (unless it is proved to hold exactly the payload: its size and SHA-256 digest; content it cannot read, or kept only in iCloud, is not proof). A failure counts as shown only once its dialog is on screen.

**Never change saved-data identifiers:** the database `application_id`, settings keys, Keychain services, widget kinds, background task and download-session IDs, the Android-format `antennapod_local:` and `antennapod_generative_cover:` prefixes, the `antennapod-subscribe` URL scheme and the `AntennaPodPage` App Intents type.

## Downloads and refresh

`MediaDownloadTransfer.download` performs one foreground transfer. Its caller owns an exclusive destination, creates the parent directory and decides whether to keep partial bytes for resuming. Retaining the transfer shares ephemeral cookies, not credentials; supply the app's User-Agent. Delegate state is mutex-protected, writes use chunks of at most 8 KiB, and progress runs on the delegate queue. The helper neither enqueues nor marks episodes downloaded.

`MediaDownloadWorker` connects transfer and store with persisted retries, logs, cancellation and cleanup. Keep one coordinator per library. Cancelling its owning `run` interrupts work; an explicit `cancel` applies the deletion and queue rules after stopping the transfer. `recoverStoppedForegroundWork` requires proof that the previous owner stopped. A request is enqueued before an existing job with the exact URL is retained; attempt identities fence stale callbacks, and completion follows a validated transfer and metadata.

`AppDelegate` retains the cross-scene `DownloadCoordinator`, the process-only warning policy, recovery, events and buffered progress; `DownloadPreferenceStore` saves preferences beside the database. The mobile-data warning bypass lasts for the process, not per row, scene or launch. Network constraints are kept per job; losing the network cancels and awaits the transfer, returns the job to waiting without a failure log, and allows resuming. Older jobs default to unmetered.

Show notes load what they reference by the Mobile updates options (`App/ShownotesNetworkPolicy.swift`): pictures, styles and fonts follow "Cover images", as on Android; media and embedded frames follow "Streaming", an intentional difference (Android loads them on any network). Scripts never load, and the formatter removes prefetch-type hints and meta refresh. WebKit content rules are installed before the first load and swapped on every change of the options or the network (unknown and offline count as restricted). When a class becomes denied, loads it already has end by replacing the document: shown notes are rebuilt at their position, and hidden notes (covered, or a pager neighbour) end them at once and rebuild when shown. Allowed classes use normal WebKit cache reuse (expired offline entries are not guaranteed, unlike Android's `LOAD_CACHE_ELSE_NETWORK`); a denied class is not shown even when cached. Ending a load is asynchronous, so there is no strict byte ceiling on a load WebKit already started. Links a person taps are unchanged.

Transcripts, external chapter JSON and a streamed episode's chapter list (read from its media) are fetched only as the Mobile updates options allow (`AuxiliaryNetworkAdmission`): transcripts and chapter JSON follow "Cover images" (an adaptation of `NetworkUtils.isEpisodeHeadDownloadAllowed`; Android's own loaders don't check the network), a streamed chapter list follows "Streaming" or the episode's Once consent, and local or cached content never asks. On a restricted network (cellular, a hotspot, Low Data Mode, offline or not yet known) a fetch takes at most 5 MiB; on an unrestricted one 20 MiB for transcripts and chapter JSON and 16 MiB for a streamed chapter list. A fetch admitted only because the network was unrestricted stops when a metered or Low Data network appears, and a deferred one waits for its permission or for an unrestricted network.

`MediaDownloadRouter` sends requests without credentials or a configured proxy to `BackgroundMediaDownloads` (one background `URLSession`, reattached at launch and by `handleEventsForBackgroundURLSession`; finished bodies wait in `media/background-transfers/` until the job's next attempt validates and publishes them; a body handed over before the first unlock keeps its response record in memory for that task until it can be written, and is an interruption, never a failure, so the system's completion handler is still called at once), and the rest to the foreground transfer. Stops never count toward the three attempts. `BackgroundWorkGrant` holds one grant of background time (UIKit's background task, `App/BackgroundWorkGrant.swift`) while sync, foreground transfers, a manual refresh, a database import, a manual export or an automatic backup the app started have work: the first participant asks for it and the others join it. When it ends (expired or refused) it is given back at once and every participant parks with its durable state (a manual refresh keeps its saved request and records nothing as failed) and resumes when a scene is active; work that starts later in the same background period parks at once instead of asking again. `DatabaseMaintenance` prunes the download log (7 days, every 3 days).

`AppDelegate` connects manual and periodic refresh, feed deletion, notifications, automatic downloads and synchronization. Queue effects apply and acknowledge atomically; other recipients keep retryable work and acknowledge completed work. `AutomaticDownloadCoordinator` consumes queue work by UUID; manual and periodic requests keep separate identities. `PeriodicFeedRefreshRuntime` includes foreground and `BGAppRefresh` adapters.

## Playback

`PlaybackCoordinator` is the shared main-actor command and event owner. It restores the selection without autoplay, serializes persistence and keeps load and queue timing, statistics, completion and streaming-consent behaviour. Commands and engine events run one after another in admission order, so every store call keeps that order; only the engine stages of pause, seek, a skip that seeks and position and state reports may run earlier, once everything admitted before them has only store writes with captured values left (a five-second save, a pause's save, a seek's or resume's recording): Pause and seek then reach the engine at once while an earlier save waits for a busy store. Loads, plays, stops, completions, resets, deletions and drains are never overtaken, and a failed write fails the playback that made it in its own turn. Generation and command IDs reject stale callbacks; readiness reconciles the current play/pause intent. Store begin/sample/end transactions keep session identity, the statistics baseline and distinct history timestamps. Saved status alone does not prove live playback.

Ordinary MP3, AAC, MP4 and other supported media share the Swift speed, skip-silence and volume processing and sample-buffer output, through native readers or the FFmpeg decoder ([DEPENDENCIES.md](DEPENDENCIES.md)). AVPlayer remains only for specific capability routes; Cast playback is owned by the receiver. Downloaded media is preferred, without silent network fallback; selected wrappers supply credentials and proxy routing. The shown and saved position counts skipped silence when its removal is heard (`PCMHeardSkips`); `HeardPlaybackRateTests` measures the speed and skip-silence heard from the rendered audio.

Volume adaptation and the sleep-timer fade follow Android's `applyVolumeAdaption` split (`VolumeControlledPCMTransport`): the renderer's own volume takes the attenuation `min(1, v)` when commanded, and the LoudnessEnhancer boost (on whenever v > 1, a 0 mB target included) applies to the PCM processed after the command (`PodcastVolumeStage`: one envelope kept across changes, a 20 ms join ramp). A gain change never flushes, re-queues or restarts the renderer, so on boosted feeds the boost part of a change is heard after the queued audio. The local/progressive AVPlayer route applies the whole gain in its tap at render time; the native-URL (HLS) route attenuates with the player's volume. At sleep-timer expiry, and when the timer's last episode completes, the coordinator pauses before it restores the volume. `VolumeOracle` (tests) checks that the renderer receives exactly the commands a test made, and the heard level against an independent model of Android's split.

An MP3 whose sample rate or channel count changes mid-file (an ad encoded differently, spliced into a show) plays as one stream in its first frame's format: the parser restarts AudioFileStream where frames at another rate begin (AudioFileStream otherwise skips them), and `NativeMP3PCMDecoder` drains and rebuilds its decoder at each change and converts other segments (two channels averaged to mono, mono copied to two, the rate converted). The timeline contract (segment origins at round(T·rate) of their exact source time, converted segments fitted to that grid when their converter output is within one frame of it (a larger difference is kept as returned and logged, and later segments move by it, so nothing is lost or repeated but later times are off by that much), seek admission per segment, seek maps, and where declared encoder delay/padding stop applying, including the unsupported spliced-header case after an indexed seek) is documented on `NativeMP3PCMDecoder`. Seek admission there drops whole MPEG frames before the target, before output grouping.

Streamed media reaches the processed sources and AVPlayer's relay routes (proxied playlists, open-ended streams) through `NativeStreamingRelay`, a loopback listener. iOS may close a suspended app's sockets while the listener still reports ready, so `StreamingRelayEligibility` (owned by `AppDelegate`, fed by every scene transition and the player's intent) retires the relays registered in `StreamingRelayReclaim` once no scene is in the foreground and nothing plays or prepares for playback the person asked for. A retired `HTTPCodecByteInput` keeps its received bytes and cursor and opens nothing until a demand (Play, a seek or a track change through `ApplicationPlaybackEngine`, or playback resuming after an interruption) starts a new listener; a local connection failure rebuilds the relay once per epoch until bytes arrive, before the retry budget, and one that persists ends as `StreamingRelayUnavailable`, whose dialog never advises re-downloading. Participants reconcile with the registry's current lifecycle (suspended, epoch), each epoch once, so a delayed notification never undoes a newer demand. AVPlayer's relay route retires its item instead and rebuilds it at the same position with the latest seek and play intent (an open-ended stream starts a new period); a refused loopback connection in its item's signals rebuilds it the same way, again only after the replacement delivered the seek or playback it was rebuilt for. An interruption during such a rebuild ends the play intent; AVPlayer routes do not resume by themselves after an interruption. Nothing keeps the app awake; Cast's relay is separate.

Cast media is routed by `CastMediaAccessOwner` (`App/CastMediaAccessOwner.swift`). An episode whose enclosure needs nothing the phone holds (no stored credentials, no app proxy, no userinfo in the raw enclosure address) is cast by its own URL and fetched by the receiver, as on Android; downloaded episodes and HLS follow the same rule. Anything else is relayed through the phone, each prepared item by its own relay, and only after the streaming admission (`AuxiliaryNetworkAdmission.streamingRelay`: "Streaming", an unrestricted network or Once consent for that episode; otherwise `CastRelayStreamingDenied`). The source (enclosure, credentials, proxy client) is read again after every await of the preparation: a change decides the route again once and a second change cancels, so a proxy configured or credentials added meanwhile never yield a direct item, and a relay already started is cancelled before it fetches anything. Userinfo never reaches the receiver: no item's content, local playback or artwork address carries it (`CastMediaItemCodec` checks). A server library's loads carry its library ID, and receiver media is adopted only by the library that loaded it (Libraries, below).

Audio dropouts are the most noticeable failure in a podcast app. Changes to the output, transports, refill, queue depth, producers or speed processing must pass `PCMRealTimeStarvationTests` and a listening check on a real iPhone. `PCMStarvationDiagnostics` logs when the renderer runs dry. The Objective-C++ render bridge keeps the [constraints below](#the-native-render-bridge).

`PlaybackSpeedPreferenceStore` is shared by `AppDelegate` and the coordinator. Keep the global, per-podcast and current-episode distinctions and the preset order; use `PlaybackSpeedPresetSelection` for full-precision edits, then `setPresets` for rounded persistence. The speed dialog uses `setSpeed(..., alsoGlobal: true)`; the lock-screen rate command changes only the current override.

`PlaybackFocusPolicy` separates play intent from temporary speech-audio suppression and computes rewind. `AudioSessionEventSource` supplies typed main-actor messages and ordered route and media-services observations. One app-wide `AudioSessionOwner` makes every activate/deactivate call, one at a time, for all engines (processed and AVPlayer), each holding a claim (`AudioSessionActivationController`). The owner itself is responsible for every activation it applied or has in flight and releases it once no live claim wants the session, so a retired engine's release, even in flight, never stops its successor, a claim closed before its request ran cannot leave the session active, and late results reconcile with current intent. The session stays active while paused and from one item to the next, as Media3 keeps audio focus: `PlaybackCoordinator` reserves it (`PlaybackSessionReserving`) before retiring the old engine for a queue handoff or episode switch, and `ApplicationPlaybackEngine` holds it through source resolution until the next item's engine takes it (an item left paused keeps it). The reservation belongs to the local route: `RoutedPlaybackEngine` withdraws it when Cast takes over, and a remote load never takes it. It is released when playback stops for good (end of queue, stop, close, failure, an abandoned replacement); an unused paused load never takes it, and system interruptions stay authoritative. An interruption's pending resumption (`PlaybackInterruptionReporting`) ends only with the interruption's end or a command of the person: Pause (the Lock Screen's too, though the player shows paused) and Stop give it up, so a late end plays nothing, and Play supersedes it; the app coming to the foreground is no evidence. A media-services reset is not a failure: the engine sets its reset fence before touching the orphaned audio objects (their cleanup errors are ignored), closes them at once and reports `mediaServicesReset`, as does `ApplicationPlaybackEngine` for a source still being resolved (whose late result is closed and never receives the earlier Play); the coordinator saves the position, clears the generation and unloads, so the episode stays selected as after a relaunch (phase `stopped`, no dialog: Play rebuilds it, seeking and skipping wait for that Play; Apple QA1749).

### The native render bridge

`Sources/NativePCMTransport/` is a small Objective-C++ target that implements the realtime-safe AVAudioSourceNode callback preferred by the iOS 27 SDK. `AVAudioSourceNode.h` marks that callback unavailable to Swift; application behavior, media-time mapping, decoding, silence/speed processing and UI stay in the Swift target.

The source uses a preallocated interleaved Float32 ring. One serialized producer publishes entire normalized PCM16 packets; one audio consumer supplies noninterleaved output. Release/acquire counters protect sample-slot ownership in both directions. The callback allocates nothing, takes no locks, calls no Swift/Objective-C methods and performs no task dispatch. The target requires lock-free UInt64 atomics and compiles the annotated callback with function-effects diagnostics as errors. These static checks and the host tests do not establish hardware latency or audio deadline performance.

Do not call enqueue concurrently from multiple producers or connect a source to concurrently rendering graphs. Control queries are atomic. A failed enqueue leaves samples and counters untouched. Underrun fills the remainder of the requested native buffer with zeroes and advances only the underrun counter, not the media-frame count. Source consumption is not hardware presentation.

Each source generation owns a distinct ring. The node's block retains that ring independently of the Objective-C control object. Never reset live cursors or reuse storage under a retained callback. The Swift owner stops and replaces the graph for seek/replacement and fences control callbacks by generation. Ordinary producer starvation refills continuously without resetting the media clock.

Mono/stereo use their standard layouts. Larger transport channel counts use explicit discrete ordering; the manual test graph also configures its mixer output explicitly to avoid automatic stereo downmix. Codec layout interpretation and device-route downmix remain separate integration gates.

Tests: `NativePCMSourceTests`, `NativePCMOutputTests` and `NativePCMPlaybackSessionTests`. `NativePCMPlaybackSession` is not connected to the app and rejects hardware mode until presentation and completion are established. The app plays through `ApplicationPlaybackEngine`, which selects the processed `PCMPlaybackEngine` (sample-buffer output) when its decoders support a source, and AVPlayer otherwise.

Render observations use a separate fixed 1024-event SPSC queue. One control consumer drains it; overflow increments an explicit counter and never stalls PCM. Native timestamp validity flags must be checked. Optional callback-cost clock fields use the SDK-annotated host clock on macOS and are zero on iOS, where that API is unavailable.

## Sync contract

`Sources/NotTennaPodCore/Sync/` holds the phone's side of the NotTennaPod server's wire contract (contract-v1), which the recording and the exchange use. The protocol is NotTennaPod-Server's `docs/PROTOCOL.md`; comments cite its sections as `PROTOCOL §N`. It has the strict JSON decoder and RFC 8785 encoder (`ContractJSON`), content hashes, receipt MACs and the digest chain (`ContractHash`), cursors (`SyncCursor`) and fact parts (`FactParts`), podcast, generation and episode IDs and GUID trimming (`ContractIdentity`), URL normalization and userinfo removal (`ContractURL`), queue keys (`QueueKey`) and the canonical queue comparators (`CanonicalQueueSort`), causal order and time normalization (`CausalOrder`), and the plain episode derivation with the server's first-item rule for repeated items in one fetch (`FetchEpisodeIdentity`). Contract strings compare by exact code points, never by Unicode canonical equivalence.

`TestSupport/Contract/vectors` is a pinned copy of the server's shared vectors, with the server commit and `SHA256SUMS`. `Tools/sync-contract-vectors.sh` refreshes it from a server checkout, and `--check` compares the copy with one. `ContractVectorTests` runs every case of each suite. `FeedParserParityTests` maps the app's feed pipeline onto the server's Android feed vectors; the differences found are recorded in `TestSupport/Contract/feed-parity-differences.json`, and the tests fail when they change. Record them again with `NTP_FEED_PARITY_RECORD=1` only after a decision about the parser.

Server libraries parse with the parity parse (`Sync/Parity/`), a port of the server's `internal/feed` Parse that passes the shared feed vectors (`ParityFeedVectorTests`); standalone libraries keep `FeedParser`. `ParityFeedParser.parse` gives a `ParityFeed` (the server's `feed.Feed`) or Android's download-error label; `podcastFields`, `episodeFields` and `occurrence(feedType:)` are the record values and occurrence a phone observes (PROTOCOL §9.4). It works on Go's semantics: strings as bytes compared exactly, and the Unicode tables, case mappings, charsets, zone data and TagSoup schema of the server's own Go build, generated into `ParityTables.swift` and `ParityCJKTables.swift` by `Tools/parity-tables.sh` from the pinned server (never edited by hand), so its output does not change with the iOS version. Any change to its output raises `ParityFeedParser.version`.

## Libraries

`Sources/NotTennaPodCore/Libraries/` holds the libraries a device keeps (PROTOCOL §15.4). The standalone library stays exactly where it always was, in Application Support (or a DEBUG test library's folder), which also holds the device settings for every library. A server library lives in `Server Libraries/<id>/` with its own `library.sqlite`, `media/`, `streaming-cache/` and `playback-library.json`, and a `staging/` folder that device backups skip (`LibraryLocation`). `libraries.json` (`LibraryRegistry`, `LibraryRegistryFile`) lists the server libraries, the active one and a recorded switch; it is written by temporary file, fsync and rename, and never in standalone use.

`AppDelegate.startLibraryGraph` asks the registry which library to open, applying a recorded switch first, and builds the graph on that library's files. When the chosen server library's folder or database is confirmed missing, this device's library opens and the first main screen a person sees says so once in the app's notice (`MissingLibraryNotice`, for the process; nothing is saved or changed). Every start, retry and restart goes through `LibraryStartup`: iOS may launch the app before the first unlock after a restart, when protected files and Keychain items cannot be read, so saved state is defaulted only when confirmed absent (`SavedState`, `ENOENT`), set aside only when its content is damaged, and never given up for the standalone library when it cannot be read now; a failed start is retired and discarded, the scenes show a wait (no error, no empty library), and the start is tried again when protected data becomes available or a scene becomes active. A failure while protected data is available is shown as before and tried again at the next activation; links, shortcuts, notifications and widget buttons that arrived meanwhile run once after the start resolves. `LibrarySwitcher` runs a switch as the database import's commit does, minus the file replacement: stop the graph, start it again. It runs only when `LibraryActivationState` allows it: nothing plays or is preparing, no player command is queued, no audio-session interruption will resume playback (`PlaybackInterruptionReporting`, read-only), no Cast session is connecting or holds media, and the app is in the foreground. It is re-checked after every player state change, Cast change and scene activation. A switch or Keep waiting for playback, a resumption after an interruption included (a Keep that stalled too, keeping its explanation), says so in its status row on the Synchronization page (`LibraryPlaybackHold`), which offers "Stop playback and continue": playback stops, then the waiting operation runs once the rule's other conditions hold, checked against a newly admitted Play in the same step. Checks run one at a time. A server library's Cast loads carry its library ID, and receiver media is adopted only by the library that loaded it, because local IDs repeat across libraries.

Each window keeps its place, as Android restores MainActivity's fragments and bottom sheet: as a scene goes to the background, `SceneDelegate.stateRestorationActivity` saves its main screen's stack (each episode screen with up to 100 pager pages either side, searches with their text), whether the player is expanded and the library's identity as a `SceneNavigationState` (activity type `org.nottennapod.app.scene-restoration`, declared in `NSUserActivityTypes`). When UIKit reconnects a session it reclaimed, or the app starts again after iOS ended it, the first main screen of the started library opens that place after the scene has given it its owners (`SceneDelegate.prepare`, `LibraryViewController+SceneRestoration.swift`): screens that read the library (a search, Discover's list) start at its first read, and a settings search's index is built again once the synchronization account is read; a scene still waiting for its library keeps the place and saves it again, and a place UIKit hands over late (before the first unlock) is taken only while nothing has moved the screen. Another library's place (after an import, a switch or a Keep) and a root page the navigation settings now hide restore nothing; at the first library read, screens whose podcast or episode is gone are left out and a gone root podcast gives way to the start page. Links, quick actions, notifications and widget buttons that come with the window run after it and decide what shows; the restored player expands only if none of them, and none of the person's navigation or player moves, came first, and until then the scene saves it as expanded. A remembered start page whose podcast is gone opens Home. A new window, or one the person closed or swiped away (UIKit discards its place), opens on the start page.

Every graph start first decides any interrupted database import (below), then migrates every library on the device to schema 22 (`LibraryGraphStart`), then finishes an unfinished "Keep using this library" at logout (`LibraryKeep`, PROTOCOL §15.4) before the registry applies a switch or anything opens. Keep is a durable transaction with a backed-up manifest in `Library Conversions/<operation>/`: capture, prepare (`previous-library.json`, markers in each `media/` and `streaming-cache/`), the archive mark, the conversion transaction in the server library's database (the commit), publication (renames under `LibraryMoveLock`, root settings from the converted library's own files, one registry write) and cleanup; every step is recognized by content when the manifest lags, and a committed Keep that could not publish opens its converted library where its markers show it. Publication is recorded in the registry's `conversions` entry (state `cleanup`), so removing the previous library never unpublishes it; each unfinished Keep runs on its own (`runUnfinished`), so an older Keep's pending cleanup never holds back a newer one. A database import publishes a pending Keep before it replaces the converted database (`LibraryGraphStart.importTarget`), and the runtime Keep retires the graph's commands in the same step as its activation check (`LibraryKeepRuntime`). The import is journaled before anything is staged (`DatabaseImportAttempt`, `Database Imports/<attempt>.json` in the root folder), with the Keychain items it creates (each before it is written) apart from the live library's credentials, which the new library retires only after publication; it holds the background grant, and background time ending before the commit rolls it back. Every graph start (`DatabaseImportRecovery`, before any library is migrated, moved by a Keep or opened) completes an interrupted import whose staged library, found by identity, became a library on the device (the replaced library's downloads and stream cache are moved aside into its staging folder before the imported library opens, and go with that folder) or rolls back one that did not (only the secrets it created that no library on the device reaches, and its staging folder); evidence it cannot read now makes the start wait, and a cleanup step that cannot run keeps the journal for a later start. What became of an interrupted import or export is kept in `pending-notices.json` (`PendingNotices`) until a person has seen it: the first main screen shows it after the missing-library message and acknowledges it once on screen in a scene that is foreground and active (the import's own result dialog acknowledges its outcome when it appears there); a background launch, a failed start or a notice waiting behind another acknowledges nothing, and a waiting notice whose scene leaves the foreground, or whose screen leaves its window, is given back for the next screen a person sees. An acknowledged attempt is remembered until its own record is resolved, so it is never shown twice. The old standalone library becomes a previous library in `Previous Libraries/<id>/`, never opened writable again, exported and removed from the Synchronization page. `LibraryGate` is held shared while an export collects its `LibraryExportSource` (one read transaction of the chosen library, found by identity, with its own speeds and credentials) and exclusively by Keep, removals, the database import, the migration of libraries that are not open and the deletion of retired feed credentials; work that background time may end waits for it cancellably (a cancelled wait holds nothing). Background transfer records name their library's identity, and every callback resolves its destination onto that library's current folder (`LibraryTransferRouting`).

Per-feed speeds and silence, the current episode with its speed and silence, and the shownotes position are library data: a server library keeps them in `playback-library.json` (`PlaybackLibraryFile`), while the standalone library keeps today's files. `AccountPolicy` is the one source of the global new-episodes action, the enqueue location and Keep sorted; its standalone backing is today's preference values. Background-transfer reconciliation keeps the transfers of every library on the device (`LibraryTransferOwnership`). `LibraryDownloadReuse` clones (APFS) the downloads of kept libraries into a new server library by feed alias and episode identity.

## Recording (server libraries)

A library is a server library when its `ntp_library` row exists (`FeedLibraryStore.isServerLibrary`); schema 19 gives every library the `ntp_*` tables (`Sync/ServerLibrarySchema.swift`, PROTOCOL §15.2), and in a standalone library they stay empty: it records and exchanges no server facts, though the visibility and derivation SQL every library shares still reads the empty tables (`LibraryReader.listedFeedCondition`, the derived triggers). Besides those tables, `ntp_registrations` maps a pending podcast registration to its local feed and registration author, and `ntp_owed` keeps facts a write that must not fail could not record (`Sync/ServerOwedFacts.swift`): a play load's queue add, with the Keep sorted policy it was made under. The failed load still settles the queue keys, so local order equals key order after every commit, and keeps the add's place as executed (PROTOCOL §7.6: the synced episodes before it up to the first registered one); every other member whose key that changed, or every member under Keep sorted, is owed a placement: a local key only, shown with the add's fact once it is recorded. If settling fails too, the queue is owed a settlement: `replayOwedFacts()` plans it off the store (the whole key assignment, `planQueueKeys`) and applies it in one short transaction only if the queue and its keys are still what it read; a write's step settles a short queue inline, and any queue write's own key sync settles it and owes what it re-keys. The replay records the owed adds at their places and shows the owed placements with them, a few members per step, owed adds first: each eligible write takes one step before its own action (never a playback write or an apply unit), and `replayOwedFacts()` takes every step, yielding the store between them so a playback save waits for one step at most, when the library opens and before the exchange pushes. Until it is recorded, owed debt is projected like a pending overlay: a pulled commit keeps an owed add queued and out of the Inbox and keeps owed members' local keys, and an unsettled queue keeps its order and keys (`ServerProjector.owedQueue`). No export includes any `ntp_*` table: the Android `.db`, OPML and HTML exports are written from the store's rows, and statistics units as the stock rows they came from (an episode with units keeps its own item above theirs, so it stays the state row when reimported).

Every store mutation runs in `FeedLibraryStore.write(_ intent:)` (`FeedLibraryStore+Recording.swift`), which in a standalone library is exactly the store's transaction. In a server library the low-level writers (`saveEpisode`, `saveHeader`, `saveQueue`, feed and episode deletion, credential installation) report into a `ChangeCapture`; before COMMIT, `record` turns the declared `ServerIntent` and the captured synced changes into facts (`Sync/ServerIntentMapping.swift`, one function per recorded intent, PROTOCOL §15.2) inside one savepoint (`LibrarySQLite.savepoint`). An explicit command (Add or Remove favorite, Remove from queue, a bulk Keep updated, a chosen New episodes action) records every episode or podcast it names, also one whose stored value already matches, as Android applies it to the whole selection. A synced change the intent does not map rolls the whole transaction back (`ServerRecordingError.unmappedChange`); a synced write outside the seam is refused. Playback writes (`beginPlayback`, saves, timeline resets, `endPlayback`, the coordinator's hooks) never fail for sync: a failed savepoint rolls back alone and sets `export_owed`.

Listening is recorded as playback sessions (PROTOCOL §8, `Sync/ServerPlaybackSessions.swift`, `ServerPlaybackHooks.swift`), each a row of `ntp_sessions`, separate from the local `LibraryPlaybackSession`. A load makes a pending session and the pending transition (`ntp_library.pending_transition`: `leave` of the loaded episode with the position claim shown at load, then `finalize` of the session once it starts; each with its `transition_id`), and closes any open session after exporting its unexported save. The coordinator's three hooks run after the engine command they follow, in its command queue, and their failures are ignored: intentional play and resume (`resume()` on a prepared engine, the `.ready` handler when playback starts; not an automatic resumption) start the pending session (`session.start` under the load's baseline, the generation token) or record a resume's claiming checkpoint (PROTOCOL §8.1); an intentional seek (`seekCurrent`) takes over from a waiting superseding claim (a seal at the pre-seek save, then a new session at the target); and `adoptRemotePosition` moves a paused, stopped or restored player to a remote position whose claim is not the library's own, never playing or preparing audio (`ServerPlaybackAdoption`, run by the app after each catch-up and whenever playback stops). Every save of an open session is journaled with its identity (PROTOCOL §6.10) and Android's contribution from the session's accounting base; a checkpoint is exported once a minute while playing (a durable transaction: a power loss loses at most about a minute) and at pause, stop, reload, timeline reset and before history and statistics cuts and position resets; `endPlayback` records exactly the pending transition's `session.end`, `session.finalize` or `episode.leave` with its own decisions (completion, `threshold_ms` from smart mark as played, the skip's queue removal). What the journal makes due is recorded in the order it was decided (`ServerTransitionState.sequence`); what a failed recording leaves is owed with the identities and times it was decided with and recorded by the next write, before anything else, and a relaunch exports what an earlier opening journaled, passively. Overlays show the position under the displayed claim, a completion only while its claim holds (a change of claim re-projects PLAYED and the queue), and played time by the server's rule: `others + Σ max(0, C − K)` over the library's sessions, `others` being the record less what the server's fold added for them (`ServerPlayedTime`), with the cuts of accepted and pending statistics resets per session. The listening marks (`ntp_local_playback`) are cleared as the recorded facts come to represent them; a save that is no listening (a paused load's) marks nothing.

`ServerOutboxWriter` builds contract-v1 envelopes (author position, previous op, sorted dependencies and targets, URL userinfo removed from every string, JCS bytes and content hash), assigns transport slots, keeps the known-node frontier (`ntp_nodes`, cuts depend on it) and writes overlays keyed by op ID. Facts about a podcast waiting for its registration are drafts on the registration's own author, with local IDs (`ntp_local_episode` placeholders, `local-episode:` overlay IDs); `resolveRegistration` materializes them in author order when the exchange applies the server's resolution. While a feed's registration still holds drafts, its later facts join that chain, and a main-author fact depends on the latest materialized draft on each subject it names, so causal order follows the person's actions whatever the clocks say. History clears and statistics resets add a deferred cut on every chain with drafts; a history removal keeps its set of cuts for Undo in memory. Every queue entry has a contract-v1 key (`ntp_queue_keys`, `Sync/ServerQueueKeys.swift`); local order equals key order, and Keep sorted and the sort sheet use the canonical comparator in a server library, with the server's durations for synced episodes (`measured_duration`, else its catalog's, else none; `canonicalSortDuration`). The server orders the queue by replaying its commands (PROTOCOL §7.6), so keys are this phone's prediction: every placement carries the `place` Android's location resolved to when it executed (`start`, `after` an episode, `end`; adds and Undo from `QueueInsertion`, moves from where the run landed), a gap next to entries the fact cannot name (local folders, another registration's episodes) projected onto the nearest nameable episode before it, and a pending registration's runs interleaved with registered members placed into their own gaps by drafts that depend on the command's main-author facts; after any main-author placement, each pending registration's queued episodes are placed again where the phone shows them by a snapshot of drafts on its chain (they depend on the command's main-author facts, so a registration pending for a whole outage settles in the phone's order; each snapshot replaces the chain's previous one, renumbering it, and there is none under Keep sorted, whose sorted adds order the queue at replay); multi-item moves carry the complete run, the sort sheet `{sort, observed}` even when it changes nothing; an add under Keep sorted inserts at its place, then sorts, and the members a command re-keyed but does not name are overlays of its first fact. Device-only entries' anchors are rewritten from the resulting queue in the same transaction (`planQueueKeys`) and again when the queue is projected. Queue facts depend on the provenance of every member they observed, before and after; placements go at most 500 to a fact. A subscription URL's userinfo becomes the subscription's credentials secret (a library credential staged before the transaction; the URL is sent without it). `ServerAccountPolicyBacking` is the `AccountPolicy` facade's server backing.

Discovery (`Sync/Discovery/`, PROTOCOL §9) changes only a server library's refresh. Its fetch parses with the parity parse (`ParityFeedParser`, `Sync/Parity/`), whose record values (`ServerCatalogParse`) it observes and identifies items by, and so does a subscription's; a first population is never filed, and is observed (listed in `ntp_observation_work`) once the podcast's first canonical metadata arrives or its 10-minute wait ends, as are the records a refresh finds while it waits. The merge (`serverMerge`) matches items by their episode derived with the podcast's `identity_rules` (`ServerEpisodeIdentity`: lookup aliases, a disputed GUID's release within 7 days, `rss-guid+enclosure`, `enclosure`; the plain identity while a registration is pending), never by AntennaPod's duplicate guesses or GUID rewrite; the first item per derived episode wins. A reused GUID seen first here (another enclosure, dates more than 7 days apart) becomes its own episode; an item gaining an enclosure is filed only if nobody acted on it; probable GUID changes (one-to-one by title and date) are observed but not filed. Each local episode's identity and the evidence it was observed with live in `ntp_local_items` (cascading with the episode). The new-episodes action alone files a release (PROTOCOL §9.10: automatic download never forces the Inbox, and the podcast settings show the real action). In the same transaction the recorder writes `catalog.observe` (records new or changed since the last parse, `ntp_observed`, and different from the canonical one; a new podcast's wait for its first canonical metadata; 200 items a fact; a batch with more than 200 to observe besides its releases lists them in `ntp_observation_work` with the parse they observe (occurrence evidence and the record's canonical bytes; a row goes only with its recording, or once proven observed or equal to the canonical record), recorded 200 to a bounded transaction by the refresh right after it commits, by a refresh answered 304, and before every push) and each `inbox`/`nothing` release's `discovery.propose`, its filing an overlay; a `queue` release is proposed with its `{key, position_id, place}` bundle by the transaction consuming its `queueEpisodes` effect, which carries the batch's evidence. A pending registration's are drafts. Every release, this phone's or an admission pulled, is one discovery ledger entry (`ntp_ledger`): the automatic download takes pending releases in place of NEW episodes, and new-episode notifications are delivered once per release (`EpisodeNotificationDelivery.deliverServerReleases`, after a refresh and when an exchange brings releases); an attach snapshot's are seen. Merges the server decides (`ServerMerges.swift`: `identity.merged_into`, `subscription.merged`) move rows, downloads, device-only settings and ledger entries to the survivor without interrupting playback; per-feed speed and skip silence, kept in the library's playback file, are listed in `ntp_feed_merges` with the merge and carried by the app (`carryServerFeedMerges`), which removes each pair only after the file is saved. A refused feed URL edit (`alias_conflict`) reverts and is a "needs attention" item naming the owner. A manual refresh also sends `POST /v1/refresh` without waiting.

Effects outside SQLite never run inside a recording transaction: file deletion is post-commit work in `pending_effects`, replayed at launch, which in a server library re-checks current references before it unlinks (`Sync/ServerPostCommitWork.swift`), and the playback coordinator unloads only after the store call returns. The recorder, failure-injection, coverage and agreement tests are `ServerRecording*Tests` and `ServerAgreementTests`; the agreement tests run the server pinned in `TestSupport/Server/server-version.txt`, built by `Tools/ntp-server.sh` from an archived copy of the sibling checkout into `.work/ntp-server/`.

## Server accounts

`Sources/NotTennaPodCore/Accounts/` signs in to a NotTennaPod server and attaches, resumes, logs out of and removes server libraries (PROTOCOL §15.4). `ServerAccounts` lives as long as the app (created at the first graph start, `App/AppDelegate+ServerAccounts.swift`) and never writes the live library. A first attachment registers the library `attaching` in `libraries.json`, stores the installation's token and transport nonce, creates the library's database in its own folder (`ServerLibraryProvisioning`), downloads and verifies the attach snapshot (`Sync/Client/ServerAttachSnapshot.swift`) and hands it to the applier (`ServerAttachSnapshotApplier`; the app passes `ServerExchangeAttachApplier`); the library then becomes `ready`, and every switch goes through `LibrarySwitcher.request` and its activation rule. Logout asks "Keep using this library" or "Go back to the library from before you signed in": both record the choice, stop the exchange, remove the token here and sign out with that token in the background, keeping the transport nonce (a removal the Keychain refuses is kept in `pending-token-removals.json` by token digest, never the token, and retried at every graph start only while the item still holds that token); going back marks the library `inactive` (logging in again resumes it), keeping marks it `keeping` until its Keep runs under the activation rule; removal deletes its folder, Keychain items and feed credentials. Every graph start resumes an interrupted attachment or removal. The device marker and each installation's token and nonce are `AfterFirstUnlockThisDeviceOnly` Keychain items (`KeychainServerSecrets`, services `org.nottennapod.app.server.device` and `org.nottennapod.app.server.token`). `ServerClient` (`Sync/Client/`) is the account endpoints' HTTP client over the synchronization transport, so proxy settings apply.

The Synchronization page's server mode is a state model (`ServerSynchronizationPage`: rows by state, the subtitle and the status row of PROTOCOL §15.5) drawn by the page's existing row view (`App/SynchronizationSettingsPresentation.swift`), with its dialogs in `App/LibraryViewController+ServerSynchronization.swift` and `App/ServerAuthenticationController.swift`. A switch the page asked for and that applies at once reopens the page in the restarted screens. The open library's exchange reports to `ServerAccounts.exchangeReported`: pauses (a server without this library's history, and, until their transition or recovery runs, a restored server, another copy using the same login and changes the server lost, show "Paused" and a "Synchronization paused" row naming the cause, which the synchronization log records as `paused <cause>`), a recovery ("Restoring…", then "Some changes could not be restored" when it finished incomplete), "Waiting for the server", the "Needs attention" count, unsent changes, a refused token ("Sign in again") and `server-status.json` in the library's folder, the last synchronization the page and the kept libraries show. A rate-limited account check (`ServerAccounts.checkAccount`) still updates the installation after an app update. The UI journeys run the pinned server through PROTOCOL §16 hub (below).

The Synchronization log and Needs attention (`App/ServerSynchronizationScreens.swift`) are settings pages over the Synchronization page, opened by their rows, by an incomplete recovery's status row (the log) and by settings search, which indexes Needs attention only while it has items. The log reads `sync.sqlite`'s `sync_log` through `ServerSyncLog` (newest first, without creating the file); Share writes it as a text file for the share sheet, under a header of what the app owns only (its version, the server address the person typed, the library's local ID; never the account name a server answered). A server's words enter it only from the protocol's vocabulary (`ServerLogValue`: error codes, push result statuses, receipt outcomes and reasons; anything else becomes a fixed description, since an answer may echo a password or the request) and a failure only by its kind, never its description; every line is also redacted where the log is written (`ServerArchive.log`: URL userinfo, `ntp1_` tokens, Bearer and Basic values, password, token and secret members), and the log keeps 30 days and at most 5,000 entries. Besides the exchange's own lines it records what the store notes, in memory until the next exchange writes it outside the write lock: writes the recorder refused (unmapped changes), owed queue additions once the transaction that recorded them committed (an ordinary write, the launch replay or the push), and one `observe` line saying why observations since the last exchange differed from the canonical records this phone holds (`ObservationDifferenceTally`: the comparisons, how many differed and the fields that differed, by name only, never a title, address or value). Needs attention reads `ntp_attention` through `FeedLibraryStore.serverAttentionItems()`: a stale subscription (its feed URL and title, kept by the retiring unit; "Subscribe again" opens the podcast's page), a refused feed URL edit naming both podcasts, every refused change as one item, and an incomplete recovery. A stale subscription subscribed again, here or on another device, resolves; Dismiss deletes an item's rows. The page's count is the list's.

Changes the server never accepts (PROTOCOL §6.13) never stall sync. No fact over the fact bound (the advertised `max_framed_fact_bytes`, at most 8 MiB, `ServerBounds.factBound`) is numbered: `ServerOutboxWriter` refuses it (`ServerRecordingError.factTooLarge`) before its first write, so a person's action that needs it changes nothing (a sort of a very long queue says "This queue is too long to sort while synchronizing with the server."); a draft's creation counts what its materialization adds, and a draft over the bound when it materializes stays a draft (`ntp_drafts.state = 'refused_too_large'`) with its overlays while the rest of its chain waits behind it. A playback session whose export is too large is marked refused (`ServerSyncSession.exportRefused`): its listening stays here and shows, nothing more of it is recorded, other sessions go on, and Needs attention names the episode with "Try again" (Synchronize now, which tries it once) and "Keep only on this device" (its listening becomes this device's own, never exported, and later history and statistics cuts here cover it). Until then a history clear, a statistics reset or a removal of that episode's history is refused whole (`cutBlockedByRefusedListening`). Observations skip an item, or the podcast record, too large for half the bound. The pusher never sends an entry over the bound (pause `change_too_large`); an `invalid_part` answer stops pushing for the rest of the exchange and sets a retry time (3 s doubling to 5 minutes, `ntp_library.push_retry_not_before`, counted per framing in `ntp_push_refusals`), and the third refusal of one framing pauses pushing (`change_refused`); both pauses let pulls go on and are cleared by Synchronize now and Force full synchronization. Refused listening of an episode the player holds when its podcast is removed is tried once more at the removal, under the generation it was played in; still too large, it goes with the detached journal, and so does its Needs attention item. Every finalization of a session kept on this device is the device's own, whenever it is made. A removal that closes the podcast of a draft chain stopped at a draft too large ends that draft (as a refused registration's drafts end) and numbers the drafts after it under the closed generation, in author order, so its item goes and nothing waits behind it, whichever phone removed the podcast; a chain another author depends on (a restored copy's fork) is left as it was, listed.

## Exchange (server libraries)

`ServerSyncEngine` (`Sync/Exchange/`) pushes, pulls and applies for one server library (PROTOCOL §6.8); `ServerSyncScheduler` decides when. It works outside the store's write lock except for apply units and small bookkeeping writes. A push first replays owed facts and runs a durable barrier, then sends the unacknowledged outbox entries in slot order within the advertised bounds; a fact over the unframed bound goes alone, one part per request, its framing transaction ID stored with the entry before the first part is sent. Receipts are stored with their lineage, and `acked_install_seq` advances over the contiguous consumed prefix. `dependency_missing`, `gap`, `invalid_part` and `payload_too_large` are retried; `version_unsupported`, 401/403, lineage answers and transport conflicts pause (`ServerPauseReason` in `ntp_library.pause_reason`); everything else backs off from 2 s to 5 minutes. `version_unsupported` pauses only what it refused (`ntp_library.version_refusals`): a refused change or push request pauses pushing, a refused pull, snapshot or secret request stops that request, and the rest goes on; a refused Force full synchronization stays owed but is not selected automatically, so incremental pulls go on; an explicit retry (Synchronize now, Force full synchronization, signing in again) clears the refusals; the page names the side: a refused change, or a whole request refused by a server whose newest protocol version (`GET /v1/info`, asked once per pause and kept in `ntp_library.protocol_version`) is older than this app's oldest, needs the server updated; any other refused request needs this app updated. A pull spools its pages to `staging/pull/`, verifies every commit against the digest chain from the cursor to the head, and archives the view in `sync.sqlite` (`Sync/Archive/ServerArchive.swift`: deflated entries and decisions with their edges, a history index, the verified commits until they are applied, the sync log and queue safeguards).

Each archived commit is applied as one unit (`Sync/Apply/`): its records become the base (`ntp_records`; episode identities are mapped in `ntp_episodes`), its nodes join the known frontier, a resolution of this library's registration materializes its drafts, this library's facts whose slots it consumed retire with their overlays (a refused queue add's members leave the queue unless an accepted membership, another pending or owed add, or the player holds them; a refused registration ends, its drafts dropped and the local state kept for the next synced action, which registers again), and the affected rows are projected again (`ServerProjector`) from the base through the remaining overlays and the player's pin. Overlays show the latest pending register value, NEW dismissed, history derived per entry while a cut or restore is pending, and only the growth since a pending statistics reset. The selected episode's position and measured duration wait (`ntp_deferred_pins`) until the player leaves it or adopts the position while not playing; a remote removal of its podcast hides the podcast from `feeds()`, `snapshot()` and statistics at once and finishes when the player leaves the episode. Rows are written with keyed statements only. PROTOCOL §6.8 asks for bounded cutovers of the live write lock; the row-write limits, pacing and per-kind time budgets here are this app's local policies for it (`ServerSyncEngine`, `ServerTransactionKind.budgets`), set from measurements, and the times given are observations or targets, not guarantees. A direct unit's statements cost what its commit changes, not what the library holds (a target of about 20 ms): the queue's projection reads the membership records that queue their episode through their own partial index (`ntp_records_in_queue`; never every episode record, nor every membership an episode ever had), a podcast's mappings are read by podcast (`ntp_episodes_by_podcast`), a projection reads and decodes each feed and episode row, record and mapping once, reads the episodes' mappings and identities and the queue members' wire IDs, queue records and overlays a few statements for all of them, an episode a commit names only for the queue is not projected as a row, and the unit prepares each distinct statement once (`LibrarySQLite.reusingStatements`). Those two indexes come with a new library's tables; a library from before them gets them at its first exchange while nothing plays, never while it opens (on a large library the build takes tens of milliseconds on the launch path), its queries correct, only slower, until then. Every synchronization transaction on the live library is measured by kind (`ServerTransactionKind`: direct units, publications, whole publications in the background, staging, rows shown ahead, hidden removals, staging take-outs, bookkeeping such as the durability barrier and push records), the longest of each in the exchange's report (`transactionTimes`, with its commit's part), and `SyncLoadStarvationTests` logs each against its kind's budget while playing (it fails only on what a person would notice: the renderer running dry, heard speed off by more than 3 %, or a hold over a second). A unit estimated above 250 row writes is built in `staging/shadow-<seq>.sqlite` on a read-only connection and published in one transaction on the attached shadow, a bounded switch that keeps concurrent local operations. The store connection logs what its writes touch (`ServerTouches`: temporary triggers on episodes, feeds, credentials, the queue and its keys and owed adds, the player, local playback marks, deferred pins, overlays, download jobs (started, stopped or moved; not progress) and recovery holds; nothing saved, its own staging and publication writes kept out). A build is a retained publication with a `ServerRetainedBasis`: the log's end taken before it reads, the scope it projected (`ServerShadowScope`: the episodes, podcasts, rows and feeds it projects or writes, the queue, the rows and feeds its plan removes, merges, transfers, holds as absent or maps anew, and the addresses of the podcasts it creates or maps anew), its projection context (`ServerProjectionContext`: the commit's statistics resets, the retirement's withdrawn queue members, a repair's snapshot semantics) and the source and target cursors. Its switch (`FeedLibraryStore.rebase`) reads the log since (bounded), ignores changes outside the scope (the player's saves and minute exports on another podcast), and re-projects the touched episodes and queue of the scope that are simple row images (a favorite, a checkpoint, a play-state change, a queue edit) from the base and current overlays with the original context, instead of writing its images of them. A touched row or feed in a structural change of its plan, a touched episode, download job or player episode (old or new selection) of a podcast its plan removes, merges, maps anew, gives credentials or changes the identity rules of (a podcast-only removal visits none of its episodes: each touched episode's podcast is read, never the podcast's episodes listed; one whose row is gone counts), a local podcast at an address it maps, a download job on an episode it projects, a podcast-level change (also on a feed it writes or maps anew that nothing maps live yet, such as a pending registration's feed a recovery's snapshot resolves, and an episode it writes that is gone since), an account-level change, recovery holds, a lost or overflowing log, or an estimated switch (its unstaged work plus re-projection, the queue counted with every member and each re-projected episode's statistics units counted per row) over the 1,000-row budget defers it (`ServerApplyError.deferred`), nothing written: kept (`ServerKeptShadow`, never built again while its source cursor is the live one), and when the budget is relaxed (no audio, no scene in the foreground) published as a whole in one transaction, its staging taken out and the unit applied from the intact local rows with its full context. A build whose own work turns out over the budget is kept unstaged for then too. Two large kinds change the library in bounded transactions behind a hidden podcast (`ntp_hidden_feeds`, left out of every library-wide read, search and statistic): a removal of more than 250 episodes hides the podcast in its unit (which reads only whether the podcast has more than 250 episodes and which of them the player holds, never their list) and deletes its rows 100 episodes at a time afterwards, newest first, each batch's statistics units first, 500 a transaction (resumed after a crash; the player's episode goes when the player leaves it); the episodes a commit creates (a new podcast, or the catalog arriving for one the library shows; each new episode hidden in `ntp_hidden_episodes` unless its podcast is hidden), their mappings and new base records, and the content records the commit changes (metadata, a measured duration, a refresh status; values, not tombstones: content no local action records a fact about or reads causally; those the base held keep their previous values and provenance in `ntp_staging`, so taking the staging out restores them exactly) are staged 100 episodes or 500 rows at a time and revealed by the unit, with what staging inserted listed in `ntp_staging` and taken out again before anything is applied if the unit never ran (and is not the kept shadow of exactly the next commit) or a feed it writes went away in between. A shown row that only that content changes (its full post-commit image equal, exactly, to its image projected from the content records alone, on the build's snapshot; not created, its play state unchanged, no structural change of the plan, not the player's) is then shown ahead of the unit, each row whole with the unit's own image, 100 rows a transaction (another device's observation that changes what episodes show, a host moving every enclosure, renamed episodes): before each transaction the local-change log is read as the switch reads it, a row touched since the build is left to the switch (which re-projects it), and a change that would defer the switch stops them (the unit is then kept for the pause, where it is published as a whole over the rows already shown). The UI is told about once a second while rows show. A staging taken out after a crash leaves rows already shown with the new content while the base has the previous records again, until the same commit publishes (its rebuilt shadow finds those rows already right) or a repair projects them; nothing anyone records depends on that content. A record, mapping or row the base already holds with exactly the same value (and provenance) is neither written nor counted against a budget; only real changes are. A unit's work counts what its rows' writes fan out to: every statistics unit row an episode's units replace deletes or inserts in either statistics table, and the statistics units a removal's cascade deletes. What a switch may write (`ServerShadowBuild.switchWork`) is the unit's work less what staging writes ahead, each staged row and record counted once and only if the unit's work counts it; admission, kept retries and the store's final check all bound that. Any other publication above 1,000 row writes changes, on more rows than one switch writes while the app is in use (1,000 row writes: about 500 episodes with their records), what a person's own actions depend on (an account-level re-projection such as a statistics reset or a history clear, listening, play-state, favorite or history changes, a queue rewrite, a merge, transfer or identity change); local actions read those (play, mark played, cleanup, the queue, statistics), so it is never shown in part: it is published whole, in one transaction, never while a scene is in the foreground. With no scene in the foreground it runs: without a limit when no audio plays, and while audio plays (the screen locked, another app in front: nobody looks at the app, playback saves can wait a few hundred milliseconds and the renderer never waits on the store) within the background budget (`backgroundPublishWorkLimit`, 24,000 row writes: a bound on work, not on time, sized so that the costliest kinds measured hold the store for an estimated half a second or so), admitted by a ticket carrying that budget (`ServerPublicationTicket.budget`) that any foreground or playback transition before its switch refuses. Nothing asks for extra background time: it runs while the app runs anyway because audio plays, and when the person leaves the app the scheduler runs what waited for that. One over the background budget, or deferred under it (a local change since its build it cannot re-project; noted on the eligibility until the next transition, so it is not tried again meanwhile), waits for a pause or stop. The page's status row says what it waits for. While audio plays, units are paced (one per 250 ms); only actual playback counts (`playsForSynchronization`: an item paused, or held silent by an interruption, does not), and a Play, or playback an interruption's end resumes, moves the publication eligibility on in the step it is admitted or reported, counting as playing until the coordinator has handled it. `ServerExchangeAttachApplier` builds a first attachment's library from its snapshot (with `ServerAttachSnapshotApplier`): entries, decisions and records streamed from the spooled pages, secrets fetched, every record projected in one transaction, the kept libraries' downloads cloned, then a catch-up.

Force full synchronization (`ServerSyncEngine+Full.swift`, `Sync/Apply/ServerFullReprojection.swift`) is this app's repair, built from a PROTOCOL §6.7 snapshot and applied by the §6.8 rules. It catches up, downloads and verifies a same-lineage `upgrade` snapshot of every field group, applies commits up to its head, fetches its secrets and completes the archive with its entries. It stages the snapshot's records in `staging/full-<seq>.sqlite` and projects every live row from them on a read-only connection (`ServerProjector` reads the staged base): every podcast and episode the snapshot holds, through the overlays and the player's pin, and the podcasts and episodes the base held and the snapshot does not are removed (local folders, unregistered previews, drafts and episodes no fact named were never projected and stay). One transaction publishes it: the record differences, the changed rows (keyed writes), the removals through the two-phase cleanup. Its switch follows the same retained-publication rules as a shadow's (the snapshot's absence and membership semantics as its context); a build it cannot publish yet is kept (`ServerKeptFull`) while the library stays at its snapshot's head, and at the pause a deferred repair is projected again as a whole inside its publication's transaction. A repair above the publication budget waits for the app to leave the foreground, and while audio plays is published whole within the background budget, as a unit's publication is; larger, it waits for a pause. The outbox is never touched.

Force full synchronization also waits by local rules (`ServerSyncEngine+Full.swift`, `ServerSyncScheduler`). A background app refresh task has seconds, so it never starts or continues a snapshot download (`snapshotsAllowed`); only the app and processing tasks do, and a repair runs only there. While audio plays a repair projects a library of at most 5,000 records (`fullStagingWhilePlaying`); a larger library, or a larger kept download, waits for a pause or stop before anything is downloaded. Once a download's first page names its head, commits after that head wait until the repair is published there (`fullSyncFence`): pushes go on, the next pull archives what follows the head, and later pulls wait for the publication. A partial download with no new page for 24 hours is abandoned (the request stays and starts again later), and a complete one holds later commits for 72 hours at most. A whole-library download (a repair's, a first attachment's or a recovery's) also waits in Low Data Mode, not only on a metered network, unless the Synchronization mobile-data preference allows sync (`bulkWaitReason`); an ordinary exchange waits only on a metered network.

A snapshot (a first attachment's, a Force full synchronization's, a recovery's) is spooled page by page (`ServerSnapshotSpool`, `Sync/Client/ServerSnapshotSpool.swift`) with a manifest written after each page, so a stopped download continues from the last page it lists; a spool is resumed or reused only for exactly the same request and is verified before any use. This bulk work never uses the free space the app keeps for its own writes (`ServerBulkDiskPolicy`, a local policy: a 1 GiB reserve for checkpoints, downloads and the library's own writes): a download starts only with room for 2.5 times the snapshot's estimate (2 GiB beyond the reserve without one), every page is checked against the staging and build it will need, and the archive batches, the staging, the build and the publication through its COMMIT write under a byte budget through the `ntp-budget` VFS (`SQLiteWriteBudget`). A write that would grow the database's files past it is refused before it happens, the transaction rolls back and the work stops with `ServerInsufficientSpace`; the verified pages stay, and it continues once space was freed.

Retained publications share one path, which a Force full synchronization and a recovery's base switch (`publishReprojection(replacing:)`) both follow: take `serverTouchWatermark()` before the build reads anything; record the build's `ServerRetainedBasis` (its `ServerShadowScope(projector, player:, live:)` with `everything` and `queue` for a whole-library projection, its `ServerProjectionContext`, `source` = the exact cursor it replaces and `target` = the snapshot head it publishes); writes to `ntp_recovery_holds` are logged as touches and defer it, so holds are dependencies (the log installs a covered table's triggers when it appears after the log started, under a new epoch, so a build from before reads its touches as unknown; creating the table before the first watermark avoids that one deferral); inside its publication transaction, check that the live cursor equals `source` exactly (epoch and digest included), call `rebase(basis, stagedWork:, workLimit:)` before writing anything, keep its writes in `quietServerTouches`, exclude `rebase.rows` from its staged row copies, write `FeedLibraryStore.plan(_:without:)` and then `writeRebase(_:basis:context:now:history:result:)`, and advance atomically to `target`; its limit is `FeedLibraryStore.publicationLimit(workLimit:ticket:)` (the caller's `workLimit` while audio plays or the app is in use, else the engine's ticket's background budget when it was admitted in the background while audio plays, else none), obtained with `largePublicationTicket(_:_:work:)` and checked with `ticket.isCurrent` inside the transaction; on `.deferred` with a limit, throw `FeedLibraryStore.deferred(_:workLimit:ticket:)` (which notes a deferral under a ticket's budget, so the engine waits for the pause), keep the build and retry at the next exchange or pause; with no limit, project again as a whole in the same transaction, as `publishFullReprojection` does.

Copies and recovery (PROTOCOL §6.10 for copies, §6.11 for recovery; `Sync/ServerCopyDetection.swift`, `Sync/ServerInstallationTransition.swift`, `ServerSyncEngine+Transition.swift`, `ServerSyncEngine+Recovery.swift`). A server library whose stored device marker is not this install's is a copy (a backup restored onto another device): at every graph start, before any library opens and after an unfinished Keep's recovery (`LibraryGraphStart.detectCopies`, skipping `keeping` libraries), and again by the exchange before it sends anything (a Keychain that cannot be read yet waits), one transaction of its own database forks every author it would write again (the main author to `T'`, each registration's current author to a fresh one whose `installation.fork {author, head}` is a draft while the registration is pending; the materializer walks a registration's chain from the copied author to its forks) and moves to a new installation `T'` with a fresh transport nonce: without a working token the transition commits there and `T'` signs in, with one it is planned. Every installation transition (`ntp_library.transition`: recovery keeps the installation's nonce, a copy or a transport conflict takes a fresh one) is issued with the predecessor's token (`POST /v1/installations/successor`, the successor's token stored under its own installation first) and committed in one transaction: the unreceipted outbox moves to `T'` from slot 1 unchanged (framing transaction IDs kept, stored parts forgotten), receipted unretired entries move to `ntp_retained`; only then does a request use `T'`'s token and the predecessor's goes. `installation_conflict`, an unexpected `installation_superseded` and a slot of this installation holding another library's fact plan a conflict transition; an already-superseded predecessor (the successor request answers `installation_superseded`, or `401` once another library used its successor) makes "Sign in again" sign in with `T'` (`signInInstallations`). Retained entries of a transition retire (overlays withdrawn, rows projected again in one unit) once the commit that accepted them was applied. `lineage_mismatch` (and a lost node this library holds) starts a recovery recorded with its plan (`ntp_library.recovery`): after the transition, the recovery snapshot answers the prefix shortcut (the cursor re-issued; only retained entries and what was archived after the old cursor are inventoried) or a full snapshot; every archived fact and decision and every retained entry is inventoried in receipt order, `bounds.recovery_inventory` at a time, and what the server needs is uploaded with its original receipt (framed facts in parts, secrets beside, `dependency_missing` retried while passes make progress), each answer kept in `sync.sqlite`'s `recovery_progress` under the server epoch it belongs to, so a crash resumes and a second restore starts the inventory again. A full recovery's snapshot is downloaded only after the uploads, so it holds what they restored, and switches the base and cursor in one retained publication (`publishReprojection(replacing:)`, below: built from the log's end taken before it reads the library, published only over exactly the cursor it was built on, the local changes since re-projected or, structural or touching a hold, deferring it; kept as `ServerKeptFull` with its recovery when it waits for the background or a pause, published at a later exchange (or by a Force full synchronization) as it was built while that cursor is live, dropped once it is not; a hold that gains no node is not written again, so the resumed recovery does not defer its own switch; over 5,000 records it is not built while audio plays); before the switch every base record whose provenance names a node still waiting for another device is held as this library had it (`ntp_recovery_holds`, `Sync/ServerRecoveryHolds.swift`), and every projection reads a held record in place of the base until a commit writes it again or none of its nodes waits; commits after it are pulled, retained entries the server took retire (refused ones keep their row as evidence), the outbox is pushed under `T'`, and `POST /v1/sync/recovery/finish {complete}` is true only if nothing ended refused. What the server refused for good (`conflict`, `invalid_receipt`, `invalid`) is quarantined at once with every fact naming it, through `previous_op_id` or a dependency (`Sync/ServerUnrestoredFacts.swift`): this library's own facts stay in `ntp_retained` marked unrestored, never sent, their overlays withdrawn, and the page says some changes could not be restored ("Needs attention" lists it). What waits for a dependency another device may restore is never given up (unsent changes never expire): the recovery says `complete: false` once, stays open and uploads it again at later exchanges with the backoff, it keeps its overlays, and the outbox facts chained behind it are parked out of the slot order (unchanged, still shown, counted as unsent; every push parks first what is newly chained) until it joins, then sent at the end of the outbox whenever a recovery catches up, a later one's included; a recovery with a parked change is not complete, and the page says changes wait for another device. In both cases a blocked author continues on a fresh one (no `installation.fork`) and blocked nodes leave the frontier, which is repaired from what they name (walking back past blocked nodes to known ones), and a node that joins comes back, so later changes keep flowing and a later Clear history or Reset statistics still observes everything known. Parking, quarantine, release and renumbering are planned on a read-only connection and done in short store transactions of at most 100 entries (`ServerBlockingSteps`): the first step alone takes the blocked tips out of the frontier as the known nodes they covered join it and moves blocked authors to fresh ones, so every committed state keeps the known past covered and a change made meanwhile is never chained behind what is blocked; a quarantine is planned from everything quarantined so far and an interrupted one completes before anything is sent; a push renumbers first, so nothing is sent with a gap. A plan made stale by facts recorded meanwhile is never applied as it was: the first step blocks those of them that name a blocked node in its own transaction, and a further pass moves them. When a hold ends and the base lacks what it held, the release projects the server's absence: a held queue membership is withdrawn and a held podcast or episode is removed through the normal removal (an episode whose identity hold ended while other fields were held is remembered in `ntp_deferred_absence` and goes with its last hold); a quarantined queue add withdraws what it showed as queued. Newer local work on a feed (a pending registration, a pending fact about its podcast or the feed) keeps the holds of that podcast and its episodes until it is resolved, so a subscription made meanwhile keeps the same feed, episodes and downloads; holds a finished recovery left this way end at later exchanges. A recovery's full publication keeps the discovery ledger exact: a row-keyed entry (a provisional release of rotating enclosures) takes the episode the snapshot maps its row to before any admission joins, and an admission the ledger lacks is a release this phone never saw, downloaded and notified once (a Force full synchronization's are seen); discovery's own changes (first admissions, occurrence corrections, podcast merges) and observation work listed at the restore come through recovery once. The publication frees every row it gives another episode before installing any binding, plans an admission whose ledger key a planned move vacates, and materializes this library's pending registrations the snapshot resolves, its projection given their podcast-to-feed bindings first (as a unit's resolution gives them); a podcast merge keeps the rows this library's unapplied observations or proposals cover by their own occurrence (with their files and jobs) until their own occurrence is resolved, a row merging only by its own binding or a derivation whose identity is its own occurrence, and a row whose occurrence the survivor holds hands its download over before the feed goes; deferred merges complete in bounded steps (`ServerDeferredMerges`: candidates and classification read off the store, one store unit each, a few an exchange). A copy restarts its recovery's phases on its own installation (`ServerRecoveryRecord.restartPhases`). Logging in again resumes the kept library of the authenticated server and account (several may share an address and username after Start over), or the one whose Log in row was chosen. `lineage_unknown`, also found when "Sign in again" reaches another account under the same name (the account made again), pauses with the page's explanation; "Start over with the server's library" signs in afresh, makes this library `inactive` with its unsent changes, and attaches to the server's library as a first attachment (`ServerAccounts.startOver`). Session copies (passive tail exports, copied pending transitions) are handled in `ServerCopyDetection`. The tests are `ServerCopyDetectionTests`, `ServerCopiesTests`, `ServerRecoveryTests`, `ServerRecoveryQuarantineTests`, `ServerRecoveryRegressionTests`, `ServerRecoveryDiscoveryTests` and `ServerStartOverTests`, against the pinned server restored with its own `backup`, `keys` and `restore` commands; `ServerRecoveryMeasurementTests` (with `NTP_EXCHANGE_MEASURE`) measures the steps' store holds beside playback saves.

`ServerSyncScheduler` (`Sync/Exchange/ServerSyncScheduler.swift`) is owned by the app core (`App/AppDelegate+ServerAccounts.swift`) for the open, active server library, whatever screen shows. It exchanges at launch, at every scene activation and when the network returns; pushes 2 s after a local action that recorded facts (the store's `serverOutboxChanges()` hint; at once with granted background time); listens to the server's change hints (`ServerEventStream`, `GET /v1/events` with the device token, server-sent events) while a scene is active and pulls when a hint names another head, polling every 60 s against a server without events or while the stream is down; retries after the engine's backoff or the server's `retry_after`; runs what waited for a pause when playback pauses, and what waited for the background when the app leaves the foreground. A pause stops every trigger until `resume()` (after "Sign in again"); a server that needs updating keeps pulling. The "Synchronization" mobile-data preference applies (`DownloadNetworkSyncGate`). Screens reload at most once a second during a catch-up; deleted feeds drain through the feed-deletion coordinator; account-policy changes reload `ServerAccountPolicyBacking`, which the library graph uses for a server library. "Synchronize now" and "Force full synchronization" on the page run at once. `BackgroundWorkGrant` holds a grant while a push waits or an exchange runs; the `org.nottennapod.app.server-sync` refresh task (30 minutes after a successful synchronization) runs one exchange, and `org.nottennapod.app.server-sync-processing` (only while a first attachment, a publication or a repair is unfinished) continues them.

The exchange tests (`ServerExchange*Tests`, `ServerSyncSchedulingServerTests`) run against the pinned server: agreement after every prefix of the recorded actions and after every step and unit of an exchange, concurrent remote changes over pending, refused and not-applied facts, scenarios 1–13 and 20–23 PROTOCOL §16 as far as the exchange reaches, crash permutations at every step, shadow publication, pins, Force full synchronization, change hints and polling. `ServerSyncSchedulerTests` check the scheduler's timing with an engine of the test's own. `ServerExchangeMeasurementTests` (set `NTP_EXCHANGE_MEASURE`) measures large commits, the live lock's hold and playback-save latency.
